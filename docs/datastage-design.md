## 1. Grounding in Real Healthtech Reference Models (v2)

This architecture is grounded in actual healthtech models (Patient, Encounter, LabResult, Referral models, and `mdm_sync` / `referral_dispatcher` services):

- **`record_type`:** Aligns directly with models: `patient`, `encounter`, `lab_result`, `referral`.
- **`record_id`:** Standardized UUID format matching underlying database entity keys.
- **`facility_id`:** Captures originating and destination healthcare facility context.
- **`golden_id`:** Generated by Master Data Management (`mdm_sync.py`) when resolving duplicate patients across facilities into a unified identity. Unauthorized access to cross-facility golden identities triggers elevated risk classification.
- **`action`:** Mapped to real clinical service operations: `view_patient`, `edit_patient`, `mdm_resolve`, `view_encounter`, `edit_encounter`, `create_encounter`, `view_lab_result`, `create_lab_result`, `view_referral`, `dispatch_referral`.
- **PHI in Cross-Facility Transit:** Inter-facility referrals (`referral_dispatcher.py`) transmit patient identifiers across systems, requiring Guardium dynamic masking and continuous DataStage auditing.

## 2. DataStage Job Flow Design

The continuous DataStage job pulls security events from the Kafka topic `healthcare-security-events` and processes records through four sequential stages (mirrored and validated in `pipeline/pipeline_validator.py`):

1. **Parse Stage (Kafka Source + JSON Parser):** Decodes incoming JSON payloads; routes malformed messages directly to a reject log without interrupting pipeline execution.
2. **Cleanse Stage (Transformer Stage):** Standardizes timestamps to ISO-8601 UTC format, lowercases roles, normalizes record type casing, and coerces authorization flags to boolean values.
3. **Normalize Stage (Transformer / Modify Stage):** Maps disparate EHR, patient portal, lab result, and prescription events into a single unified record format; appends `source_system` and `ingested_at`.
4. **Quality Check Stage (Constraint Stage):** Evaluates completeness and validity against standard schemas. Records are tagged `CLEAN`, `FLAGGED`, or `DROPPED` and routed accordingly.

## 3. watsonx.data Storage Architecture (Apache Iceberg)

All events are loaded into **IBM watsonx.data** backed by **Apache Iceberg** tables:

### A. `security_events` Table
Primary operational table storing normalized events with quality status metadata. Partitioned by `event_date` for high-performance temporal scans.

### B. `audit_log` Table (Immutable Audit Ledger)
An **append-only, immutable audit ledger** tracking every access request and database query against patient records.
- **Append-Only Policy:** No `UPDATE` or `DELETE` operations are permitted on this table.
- **Iceberg Snapshot Isolation:** Guarantees tamper-evident, historical audit logging for HIPAA compliance reviews (45 CFR § 164.312(b)).

#### Schema Definition

```sql
CREATE TABLE watsonx_data.healthcare_analytics.audit_log (
    event_id VARCHAR(36),
    event_timestamp TIMESTAMP,
    event_date DATE,
    user_id VARCHAR(64),
    user_role VARCHAR(32),
    action VARCHAR(64),
    record_type VARCHAR(32),
    record_id VARCHAR(64),
    facility_id VARCHAR(64),
    golden_id VARCHAR(64),
    authorized BOOLEAN,
    is_violation BOOLEAN,
    risk_tier VARCHAR(16),
    masking_applied BOOLEAN,
    source_system VARCHAR(32),
    quality_status VARCHAR(16),
    ingested_at TIMESTAMP
)
USING ICEBERG
PARTITIONED BY (event_date);
```

## 4. Compliance Analytics Layer & SQL Queries

The live compliance analytics layer queries the `audit_log` table via Presto / Trino in watsonx.data to feed the **IBM Cognos Clinical Security Officer Dashboard**.

### Query 1: Daily Violation Trend
```sql
SELECT 
    event_date,
    COUNT(*) AS total_violations,
    COUNT(DISTINCT user_id) AS distinct_violators,
    COUNT(DISTINCT record_id) AS impacted_records
FROM watsonx_data.healthcare_analytics.audit_log
WHERE is_violation = TRUE OR authorized = FALSE
GROUP BY event_date
ORDER BY event_date DESC;
```

### Query 2: Risk Tier Distribution
```sql
SELECT 
    risk_tier,
    COUNT(*) AS event_count,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2) AS percentage
FROM watsonx_data.healthcare_analytics.audit_log
GROUP BY risk_tier
ORDER BY event_count DESC;
```

### Query 3: Top Policy Violators by Role
```sql
SELECT 
    user_id,
    user_role,
    COUNT(*) AS violation_count,
    MAX(event_timestamp) AS last_violation_time
FROM watsonx_data.healthcare_analytics.audit_log
WHERE is_violation = TRUE OR authorized = FALSE
GROUP BY user_id, user_role
ORDER BY violation_count DESC
LIMIT 10;
```

### Query 4: Real-Time Incident Investigation Feed (High/Critical Risk)
```sql
SELECT 
    event_id,
    event_timestamp,
    user_id,
    user_role,
    action,
    record_type,
    record_id,
    facility_id,
    golden_id,
    risk_tier,
    masking_applied,
    source_system
FROM watsonx_data.healthcare_analytics.audit_log
WHERE risk_tier IN ('HIGH', 'CRITICAL') OR is_violation = TRUE
ORDER BY event_timestamp DESC
LIMIT 25;
```

## 5. Risk Tier Categorization Logic

| Risk Tier | Criteria | Example Trigger |
|---|---|---|
| **CRITICAL** | SQL Injection, mass patient exfiltration | S-TAP blocked SQLi, >= 50 records exported |
| **HIGH** | Unauthorized cross-facility access (`golden_id`), `mdm_resolve`, `dispatch_referral`, bulk downloads | `QR-RULE-102`, `QR-RULE-103` offenses |
| **MEDIUM** | Unauthorized single-facility record lookup, off-hours access | `QR-RULE-101`, `QR-RULE-104` offenses |
| **LOW** | Authorized clinical activity, routine logins | Normal physician patient view |
